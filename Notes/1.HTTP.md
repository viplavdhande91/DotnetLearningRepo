## 1. What are HTTP Methods?

1. HTTP methods (also called verbs) are standardized request types that tell the server **what action to perform on a resource**.
2. They are the backbone of **RESTful APIs**: the URL identifies the *resource*, the method says what to *do* with it.
3. Typical operations: retrieve data, create, update (fully or partially), delete, inspect metadata, discover allowed operations.
4. In ASP.NET Core Web API, each action method is mapped to a verb using an attribute: `[HttpGet]`, `[HttpPost]`, `[HttpPut]`, `[HttpPatch]`, `[HttpDelete]`, `[HttpHead]`, `[HttpOptions]`.

---

## 2. The 7 Common Methods

### 2.1 GET

1. **Purpose:** Retrieve data without modifying anything.
2. Safe to call any number of times, as it doesn't change server state.
3. Example: fetch the list of all users or one product by ID.
4. Attribute: `[HttpGet]`

### 2.2 POST

1. **Purpose:** Send data to the server to **create a new resource**.
2. Data travels in the **request body**; its format is declared by the `Content-Type` header.
3. Example: submitting a registration form creates a new user.
4. Every call creates a *new* entry, so repeating it produces duplicates.
5. Attribute: `[HttpPost]`

### 2.3 PUT

1. **Purpose:** **Replace the entire resource** with the payload sent.
2. Normally used to update an existing resource. Depending on the server implementation, it may create the resource if it doesn't exist at that URI.
3. Because it is a full replacement, the client must send **all** fields.
4. Example: overwrite a user's whole profile with new data.
5. Attribute: `[HttpPut]`

### 2.4 PATCH

1. **Purpose:** **Partial update**. Send only the changes, not the whole resource.
2. Unlike PUT, other fields are left untouched.
3. Example: update only the email of a user profile.
4. Attribute: `[HttpPatch]`

### 2.5 DELETE

1. **Purpose:** Remove the specified resource from the server.
2. Example: delete a user account from the database.
3. Attribute: `[HttpDelete]`

### 2.6 HEAD

1. **Purpose:** Same as GET, but returns **only the headers, no response body**.
2. Used to check metadata such as `Content-Type` and `Content-Length` before doing a full GET.
3. Example: check the size of a large file before deciding to download it.
4. Attribute: `[HttpHead]`

### 2.7 OPTIONS

1. **Purpose:** Describes the communication options available for a resource, i.e. which methods the server supports.
2. Heavily used in **CORS preflight requests** to check which methods and headers are allowed.
3. Example: check whether PUT is supported on an endpoint before attempting an update.
4. Attribute: `[HttpOptions]`

## 4. Safe vs Unsafe Methods

Classification is based on **whether the method changes server state**.

### Safe methods (read-only, no side effects)

1. **GET**: retrieves data.
2. **HEAD**: retrieves metadata only.
3. **OPTIONS**: describes communication options.

### Unsafe methods (can add, modify, or delete data)

1. **POST**: creates a resource.
2. **PUT**: replaces a resource.
3. **PATCH**: partially updates a resource.
4. **DELETE**: removes a resource.

> Use unsafe methods with care, since they change or destroy data.

---

## 5. Idempotent vs Non-Idempotent Methods

**Definition:** A method is **idempotent** if calling it once or many times with the same input leaves the server in the **same final state**.

### Idempotent methods

1. **GET**: repeated reads return the same data (unless something else changed it in between).
2. **PUT**: sending the same full payload repeatedly leaves the resource in the same state. Example: setting a product price to 500 ten times is the same as doing it once.
3. **DELETE**: after the first delete, the resource is gone, so further deletes change nothing more.
4. **HEAD**: same as GET, just without a body.
5. **OPTIONS**: querying options repeatedly changes nothing.
6. **PATCH: it depends.**
   - Idempotent when it *sets* a value. Example: set status to `"active"`.
   - **Not** idempotent when it *accumulates*. Example: increment a login count.

### Non-idempotent method

1. **POST**: repeating the same request typically creates multiple new resources. Example: submitting a form twice creates two records.

---

## 6. Idempotency vs Safety

| Concept         | Meaning                                                      | Examples                |
|-----------------|--------------------------------------------------------------|-------------------------|
| **Safe**        | Does not modify server state                                 | GET, HEAD, OPTIONS      |
| **Idempotent**  | Repeating the request has the same effect as sending it once | GET, PUT, DELETE, HEAD, OPTIONS |

Key combinations to remember:

1. **Safe and idempotent:** GET (also HEAD, OPTIONS).
2. **Unsafe but idempotent:** PUT, DELETE.
3. **Unsafe and non-idempotent:** POST.
4. **PATCH:** unsafe, idempotent only depending on the operation.

> **Memory trick:** *All safe methods are idempotent, but not all idempotent methods are safe.*

## 7. Real-Time Example: Product Management API

A simple CRUD system built with **ASP.NET Core Web API + EF Core + SQL Server**, demonstrating all 7 methods.

### 7.1 Project structure

1. **Models:** `Product` entity.
2. **Data:** `ProductDbContext` (EF Core).
3. **Controllers:** `ProductsController` with one action per HTTP method.
4. **Program.cs:** service registration and middleware pipeline.

### 7.2 Packages

```powershell
Install-Package Microsoft.EntityFrameworkCore.SqlServer
Install-Package Microsoft.EntityFrameworkCore.Tools
```

### 7.3 Model (`Product.cs`)

```csharp
public class Product
{
    [Key]
    public int Id { get; set; }

    [Required, StringLength(100)]
    public string Name { get; set; }

    [Required]
    [Column(TypeName = "decimal(18,2)")]
    public decimal Price { get; set; }

    public string? Description { get; set; }
}
```

### 7.4 DbContext

1. Inherits from `DbContext` and takes `DbContextOptions<ProductDbContext>` in the constructor.
2. Exposes `DbSet<Product> Products`.
3. `OnModelCreating` seeds two sample products (Laptop, Smartphone) using `HasData`.

### 7.5 Configuration and DI (`Program.cs`)

1. `AddControllers()` registers controllers. The example also sets `PropertyNamingPolicy = null` to keep original property casing in JSON.
2. `AddDbContext<ProductDbContext>(...UseSqlServer(connectionString))` registers the context with DI.
3. Connection string lives in `appsettings.json` under `ConnectionStrings`.
4. Swagger is enabled in the Development environment.
5. Pipeline: `UseHttpsRedirection()` → `UseAuthorization()` → `MapControllers()`.

### 7.6 Migrations

```powershell
Add-Migration InitialCreate
Update-Database
```

Creates the `ProductDB` database and the `Products` table.

### 7.7 Controller skeleton

```csharp
[Route("api/[controller]")]
[ApiController]
public class ProductsController : ControllerBase
{
    private readonly ProductDbContext _context;
    public ProductsController(ProductDbContext context) => _context = context;
    // actions below
}
```

### 7.8 Action-by-action summary

| Action | Route | Behaviour | Responses |
|--------|-------|-----------|-----------|
| `GET` all | `api/products` | `ToListAsync()` | `200 OK` + list; `500` on error |
| `GET` by id | `api/products/{id}` | `FindAsync(id)` | `200 OK`; `404` if missing |
| `POST` | `api/products` | Validate → `AddAsync` → `SaveChangesAsync` | `201 Created` via `CreatedAtAction` (with Location header); `400` if invalid |
| `PUT` | `api/products/{id}` | Check id matches body → find → overwrite **all** fields → save | `204 No Content`; `400` on id mismatch; `404` if missing |
| `PATCH` | `api/products/{id}` | Check id → find → update **only Price** → save | `204 No Content`; `400`; `404` |
| `DELETE` | `api/products/{id}` | Find → `Remove` → save | `204 No Content`; `404` if missing |
| `HEAD` | `api/products/{id}` | `AnyAsync` check → add headers → return OK, no body | `200 OK`; `404` |
| `OPTIONS` | `api/products` | Adds `Allow` header listing supported methods | `200 OK` |

### 7.9 Key code patterns

**POST: return 201 with a Location header**

```csharp
return CreatedAtAction(nameof(GetProductById), new { id = product.Id }, product);
```

**PUT: full replacement**

```csharp
existing.Name = product.Name;
existing.Price = product.Price;
existing.Description = product.Description;
await _context.SaveChangesAsync();
return NoContent();
```

**PATCH: partial update (only price)**

```csharp
existing.Price = product.Price;   // other fields untouched
await _context.SaveChangesAsync();
return NoContent();
```

**OPTIONS: advertise allowed methods**

```csharp
Response.Headers.Append("Allow", "GET, POST, PUT, PATCH, DELETE, OPTIONS, HEAD");
return Ok();
```

### 7.10 Error-handling pattern used

1. Wrap each action in `try/catch`.
2. Return `500` with a message plus details on unexpected exceptions.
3. Catch `DbUpdateException` separately on write operations (PUT, PATCH, DELETE) to surface the inner exception.
4. Return `404` with a descriptive message when the resource isn't found.
5. Return `400` for validation failures (`ModelState`) or ID mismatch.

> In production, don't leak `ex.Message` to clients. Log the details and return a generic message (or use global exception handling or `ProblemDetails`).

## 9. Best Practices

1. **GET:** only for safe, read-only operations. Never change data in a GET.
2. **POST:** create new resources or submit data for processing.
3. **PUT:** replace or update an existing resource **completely**.
4. **PATCH:** partial updates when only a few fields change.
5. **DELETE:** remove a resource.
6. **OPTIONS:** discover supported methods (CORS preflight).
7. **HEAD:** fetch metadata only, without downloading content.

## 10. Interview Q&A

**Q1. What are HTTP methods?**
- Standard request types that tell the server what action to perform on a resource. They are the foundation of RESTful design.

**Q2. How do you map an action to an HTTP method in ASP.NET Core?**
- Use attributes such as `[HttpGet]`, `[HttpPost]`, `[HttpPut]`, `[HttpPatch]`, `[HttpDelete]`, `[HttpHead]`, `[HttpOptions]`, optionally with a route template, e.g. `[HttpGet("{id}")]`.

**Q3. What is the difference between PUT and PATCH?**
- PUT replaces the **entire** resource (client sends all fields). PATCH applies a **partial** update (only the changed fields). PUT is always idempotent; PATCH may or may not be.

**Q4. What is the difference between PUT and POST?**
- POST creates a new resource, and the server usually decides its URI and ID, so repeating it creates duplicates (non-idempotent). PUT targets a specific URI and replaces what's there, so repeating it gives the same result (idempotent).

**Q5. What does "safe" mean for an HTTP method?**
- It doesn't modify server state. GET, HEAD and OPTIONS are safe.

**Q6. What does "idempotent" mean?**
- Making the same request multiple times has the same effect on server state as making it once. GET, PUT, DELETE, HEAD and OPTIONS are idempotent. POST is not. PATCH depends.

**Q7. Is DELETE - idempotent? The second call returns 404, so how?**
- Yes. Idempotency is about **server state**, not the response code. After the first call the resource is gone, and later calls leave the state unchanged (even though the response may be 404).

**Q8. Give an example of a PATCH that is idempotent and one that isn't.**
- Idempotent: set status to `"active"`. Not idempotent: increment a login counter.

**Q9. Can a method be idempotent but not safe?**
- Yes. PUT and DELETE change state but repeating them has no additional effect. The reverse is not possible: every safe method is idempotent.

**Q10. What is the difference between GET and HEAD?**
- HEAD returns the same headers as GET but **no body**. It's used to check metadata (size, type, existence) cheaply.

**Q11. What is the OPTIONS method used for?**
- To ask the server which methods and headers are supported for a resource. Browsers send it as a **CORS preflight** request before certain cross-origin requests.

**Q12. Which status code should POST return on success?**
- `201 Created`, with a `Location` header pointing to the new resource. In ASP.NET Core use `CreatedAtAction` or `CreatedAtRoute`.

**Q13. Which status code do PUT, PATCH and DELETE usually return?**
- `204 No Content` when there's nothing to return. `200 OK` with the updated resource is also valid.

**Q14. Why is POST not idempotent, and how can you make it safe for retries?**
- Each call creates a new resource. To make retries safe, use an **idempotency key** (client sends a unique key; the server stores it and ignores duplicates). **(Extra)**

**Q15. Why shouldn't you use GET to modify data?**
- GET is expected to be safe. Browsers, proxies, crawlers and caches may call or prefetch it freely, so a state-changing GET can cause accidental data changes. Parameters also appear in URLs and logs.

**Q16. Where does a POST payload go, and how does ASP.NET Core read it?**
- In the request body. `[FromBody]` binds it, using the `Content-Type` header (e.g. `application/json`) to pick the input formatter.

**Q17. What does `[ApiController]` give you here?**
- Automatic model validation (400 responses), binding source inference, attribute routing requirement, and `ProblemDetails` for errors. **(Extra)**

**Q18. How do you restrict an endpoint to certain methods?**
- Use the specific verb attribute. A request with another verb gets `405 Method Not Allowed`. **(Extra)**

## 11. Common Pitfalls / Gotchas

1. **Idempotent ≠ same response.** It refers to server state, not the status code or body returned.
2. **PATCH is not automatically idempotent.** It depends on the operation.
3. **PUT needs the full object.** Missing fields may be overwritten with null or default values.
4. **Return the right status code.** Use 201 for create, 204 for update or delete with no body, 404 for a missing resource, 400 for bad input.
5. **ID mismatch check.** In PUT and PATCH, verify the route `id` matches the body `id` (as the example does).
6. **Don't leak exception details** (`ex.Message`) in production responses.
7. **Avoid binding the entity directly** from the request in real projects. Use DTOs to prevent over-posting and to control which fields are exposed. **(Extra)**
8. **Real PATCH implementations:** the tutorial's PATCH action takes a whole `Product` and only reads `Price`, which is a simplification. The standard approach is JSON Patch (`JsonPatchDocument<T>`, `application/json-patch+json`) or a dedicated partial-update DTO. **(Extra)**
9. **HEAD action detail:** the tutorial sets `Content-Length` manually from a serialized value, which is only for demonstration and not a real size of the resource. **(Extra)**
10. **Don't confuse the attribute spelling:** it is `[HttpOptions]` (the source text has a typo, "HttpOtions").

## 12. One-Minute Revision Cheat Sheet

```
GET      -> read              | safe   | idempotent
POST     -> create            | unsafe | NOT idempotent
PUT      -> replace whole     | unsafe | idempotent
PATCH    -> partial update    | unsafe | depends
DELETE   -> remove            | unsafe | idempotent
HEAD     -> headers only      | safe   | idempotent
OPTIONS  -> allowed methods   | safe   | idempotent  (CORS preflight)
```

- **Safe:** GET, HEAD, OPTIONS
- **Unsafe:** POST, PUT, PATCH, DELETE
- **Idempotent:** GET, PUT, DELETE, HEAD, OPTIONS (+ PATCH sometimes)
- **Non-idempotent:** POST
- **Success codes:** GET 200 · POST 201 · PUT/PATCH/DELETE 204 · HEAD/OPTIONS 200
- **Rule of thumb:** safe ⊂ idempotent
