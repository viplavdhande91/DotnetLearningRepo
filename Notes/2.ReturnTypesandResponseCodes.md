## 1. What is a Return Type?

1. Every controller action must return **something** to the client: a simple value, an object, or an HTTP response.
2. That "something" is the action's **return type**. It defines **what** data is sent and **how** the HTTP response behaves.
3. ASP.NET Core serializes the returned value to **JSON** (or XML if configured) and writes it to the response body.
4. The return type determines:
   1. The **HTTP status code** (success, failure, error).
   2. The **response body** (data or message).
   3. How the **client reacts**, since clients rely on the status code and body to decide what to do next.
5. Think of the return type as the **contract / promise** between your API and its consumers.

---

## 2. Why Return Type Choice Matters

1. **Clarity:** consumers instantly know what to expect (string, object, HTTP result).
2. **Better error handling:** you can send 404, 400, 201 and so on instead of always 200 OK.
3. **Client experience:** predictable, consistent response structure for browsers, Postman, mobile apps.
4. **Maintainability:** standardized types make the API easier to evolve, debug and document (Swagger/OpenAPI).

---

## 3. The Categories at a Glance

1. **Specific types:** `string`, `int`, `Product`, `List<Product>`, etc.
2. **`IActionResult` / `ActionResult`:** full control over status code, body and headers.
3. **`ActionResult<T>`:** typed data **plus** HTTP control (introduced in **ASP.NET Core 2.1**).
4. **Async wrappers:** any of the above inside `Task` / `Task<T>`.

## 5. Primitive / Complex (Specific) Types

### 5.1 What it is

1. The action returns the data directly, e.g. `int`, `string`, `Product`, `List<Product>`.
2. The framework serializes it to JSON automatically. For example, an `int` 5 becomes just `5`, and a `Product` becomes a JSON object.

### 5.2 Automatic status codes

| Situation | Status code |
|-----------|-------------|
| Method returns a value | **200 OK** |
| Method returns `null` (reference type) | **204 No Content** |

### 5.3 Example

```csharp
[HttpGet("GetProductById/{id}")]
public async Task<Product?> GetProductById(int id)
{
    return await ProductService.GetProductByIdAsync(id);
}
```

### 5.4 When to use

1. Simple or prototype APIs, learning projects.
2. Internal tools that don't need strict REST semantics.
3. Endpoints that **always succeed** (e.g. a count of a fixed list).
4. Small proofs-of-concept.

### 5.5 Limitations

1. **No control over status codes:** can't return 404, 400 or 201. A missing product silently becomes **204**.
2. **No standard error format:** can't produce `ProblemDetails` (RFC 7807) style errors.
3. **No custom headers or metadata:** e.g. `Location` (created resource), `ETag` (caching), `X-Total-Count` (pagination).
4. **Not suitable for production/public REST APIs.**
5. **Clients can't reliably tell success from failure:** everything looks like 200 or 204.

## 6. IActionResult

### 6.1 What it is

1. An **interface** representing the result of an action.
2. Gives **complete control** over:
   1. **Status code**
   2. **Response body**
   3. **Headers**
3. You return helper results such as `Ok()`, `NotFound()`, `BadRequest()`, `NoContent()`, `CreatedAtAction()`.

### 6.2 When to use

1. **Multiple outcomes** are possible (200 vs 404).
2. **Error handling** and validation feedback matter.
3. **Custom status codes** are needed (201, 202, 500).
4. **POST / PUT / DELETE** operations with conditional results (success, validation error, conflict).
5. **Consistent HTTP behaviour** that frontends and tools expect.

### 6.3 Example

```csharp
[HttpGet("GetProductById/{id}")]
public async Task<IActionResult> GetProductById(int id)
{
    var product = await ProductService.GetProductByIdAsync(id);

    if (product == null)
        return NotFound($"Product with ID = {id} was not found.");

    return Ok(product);
}
```

Primitives must be wrapped too: `return Ok(count);`

### 6.4 Limitations

1. **No compile-time type safety:** you can return *anything* inside `Ok(...)`.
2. **Weak Swagger/OpenAPI schema:** the response shows as a generic `object` unless you add `[ProducesResponseType]`.

## 7. ActionResult (Non-Generic)

### 7.1 What it is

1. A **base class** for the built-in result types: `OkResult`, `NotFoundResult`, `BadRequestResult`, `NoContentResult`, and so on.
2. Lets you send different HTTP responses **without being tied to a data type**.
3. At runtime the framework inspects which subclass you returned and writes the matching status code and body.

> **(Correction)** The article calls it a "concrete class". In the framework it is an **`abstract` class** that implements `IActionResult`.

### 7.2 When to use

1. When the method's job is to **perform an action**, not return a dataset.
2. When you don't need typed data and only report **success or failure** (`Ok()`, `BadRequest()`, `NotFound()`).
3. For **POST / PUT / DELETE** with binary outcomes: 201 or 200 on success, 400 on bad input, 404 when missing.

### 7.3 Example

```csharp
[HttpGet("GetProductDetails/{id}")]
public async Task<ActionResult> GetProductDetails(int id)
{
    if (id <= 0)
        return BadRequest("Invalid product ID.");

    var product = await ProductService.GetProductByIdAsync(id);
    if (product == null)
        return NotFound($"Product with ID = {id} not found.");

    return Ok(product);
}
```

### 7.4 Limitations

1. **No compile-time type safety:** nothing stops you returning a string instead of a `Product`.
2. **Swagger shows `object`:** needs manual `[ProducesResponseType(typeof(Product), 200)]`.
3. **Hard for API consumers:** generated TypeScript or SDK clients treat the response as `any`.
4. **Not ideal for GET endpoints** whose purpose is returning data. Use `ActionResult<T>`.

### 7.5 `IActionResult` vs `ActionResult`

| Point | `IActionResult` | `ActionResult` |
|-------|-----------------|----------------|
| Kind | Interface | Base class (abstract) |
| Represents | Any possible action result | Base for the built-in framework results |
| Custom result types | Easy (implement the interface) | Usually uses predefined results |
| Type safety | None | None |
| Role | General or custom responses | Foundation for `ActionResult<T>`; standard REST-style responses |

## 8. ActionResult&lt;T&gt;

### 8.1 What it is

1. A **generic** return type introduced in **ASP.NET Core 2.1**.
2. Combines:
   1. **Strong typing** (the compiler and Swagger know `T`).
   2. **HTTP control** (`Ok()`, `NotFound()`, `BadRequest()`, etc.).
3. Can represent either:
   1. A successful value of type `T`, or
   2. Any HTTP-specific result (any `ActionResult`).
4. Solves the old trade-off:
   1. `Task<Product>` is simple but always 200 (or 204).
   2. `Task<IActionResult>` is flexible but untyped.
   3. **`Task<ActionResult<Product>>` gives both.**

### 8.2 Example

```csharp
[HttpGet("GetProductById/{id}")]
public async Task<ActionResult<Product>> GetProductById(int id)
{
    if (id <= 0)
        return BadRequest("Invalid Product ID. It must be greater than zero.");

    var product = await ProductService.GetProductByIdAsync(id);

    if (product == null)
        return NotFound($"Product with ID = {id} not found.");

    return Ok(product);   // 200 OK, JSON body
}
```

### 8.3 When to use

1. **Real-world REST APIs** that return data and handle errors (404, 400, 200, 204).
2. When you want **strong typing and Swagger-friendly docs**. Swagger shows e.g. `200: Product`, `400: ProblemDetails`, `404: ProblemDetails`.
3. For **clean success/failure handling** in one typed signature.
4. When you need **compile-time checking** of the success type.
5. For GET, POST, PUT and even some DELETE endpoints.

### 8.4 Why it's the recommended default

1. Type safety **plus** full HTTP control.
2. Accurate Swagger/OpenAPI schema and better generated client SDKs.
3. Self-documenting method signatures.

> **(Correction)** The article says `return Ok("Wrong type");` inside an `ActionResult<Product>` method triggers a compile-time error. It does **not**, because `Ok(object)` returns an `OkObjectResult`, which is accepted. The compile-time check only applies when you return a **raw value**:
>
> ```csharp
> public ActionResult<Product> Get()
> {
>     return "oops";            // compile error: string is not Product
>     return Ok("oops");        // compiles (checked only by tests or Swagger)
>     return new Product();     // OK: implicit conversion to ActionResult<Product>
> }
> ```
>
> **(Extra)** Returning the raw object (`return product;`) is also valid and slightly cleaner than `Ok(product)`.

## 9. Asynchronous Return Types

1. Any category can be wrapped in `Task` / `Task<T>`:
   1. `Task<int>`
   2. `Task<IActionResult>` / `Task<ActionResult>`
   3. `Task<ActionResult<Product>>`
2. **Why:** non-blocking I/O (DB queries, external API calls) **frees threads while waiting**, improving scalability and performance.
3. Use `async` / `await` on the action and `await` the service call.

---

## 10. Comparison Table

| Feature | Specific type (`Product`) | `IActionResult` | `ActionResult` | `ActionResult<T>` |
|---------|---------------------------|-----------------|----------------|-------------------|
| Custom status codes | No | Yes | Yes | Yes |
| Compile-time type safety | Yes | No | No | Yes (for raw returns) |
| Accurate Swagger schema | Yes (200 only) | No (object) | No (object) | Yes |
| Return `NotFound()` etc. | No | Yes | Yes | Yes |
| Custom headers | No | Yes | Yes | Yes |
| Best for | Prototypes, always-succeed endpoints | General or custom responses | Action-style endpoints | **Production APIs returning data** |

---

## 11. Helper Methods and Their Status Codes

| Helper | Status | Typical use |
|--------|--------|-------------|
| `Ok(obj)` | 200 OK | Successful read or update returning data |
| `CreatedAtAction(...)` | 201 Created | After POST; adds `Location` header |
| `NoContent()` | 204 No Content | Success with nothing to return, or empty list |
| `BadRequest(...)` | 400 Bad Request | Invalid input |
| `NotFound(...)` | 404 Not Found | Resource missing |
| `StatusCode(500, ...)` | 500 | Unexpected server error |

Default behaviours of **specific types**:

1. Returns a value gives **200**.
2. Returns `null` (reference type) gives **204**.

---

## 12. Which One to Choose?

1. **Prototype, learning, or always-succeeds endpoint:** primitive or complex type.
2. **Flexible HTTP responses, or custom result types:** `IActionResult`.
3. **Action-style endpoints with no typed payload:** `ActionResult`.
4. **Production APIs returning data (default choice):** **`ActionResult<T>`**, wrapped in `Task` for async.

> **(Extra)** Also pair with `[ProducesResponseType(...)]` (or `[ProducesResponseType<T>]` in newer .NET) to document error codes like 400, 404 and 500 that `ActionResult<T>` can't infer by itself.
