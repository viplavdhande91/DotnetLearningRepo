# .NET Dependency Injection — Guidelines & Best Practices

This guide summarizes **recommended practices for using Dependency Injection (DI) in .NET applications**.

---

# Designing Services for DI

When designing services for dependency injection:

### Avoid Static and Global State

Do not use static classes or global state.

Bad example:

```csharp
public static class LoggerService
{
    public static void Log(string message)
    {
        Console.WriteLine(message);
    }
}
````

Better approach using DI:

```csharp
public interface ILoggerService
{
    void Log(string message);
}

public class LoggerService : ILoggerService
{
    public void Log(string message)
    {
        Console.WriteLine(message);
    }
}
```

Registration:

```csharp
builder.Services.AddSingleton<ILoggerService, LoggerService>();
```

Usage:

```csharp
public class OrderService
{
    private readonly ILoggerService _logger;

    public OrderService(ILoggerService logger)
    {
        _logger = logger;
    }

    public void ProcessOrder()
    {
        _logger.Log("Order processed");
    }
}
```

---

### Avoid Direct Instantiation

Do not create dependencies manually inside services.

Bad example:

```csharp
public class OrderService
{
    private readonly EmailService _emailService = new EmailService();

    public void Process()
    {
        _emailService.Send();
    }
}
```

Correct approach using DI:

```csharp
public class OrderService
{
    private readonly IEmailService _emailService;

    public OrderService(IEmailService emailService)
    {
        _emailService = emailService;
    }

    public void Process()
    {
        _emailService.Send();
    }
}
```

---

### Keep Services Small

If a class has **many dependencies**, it likely has too many responsibilities.

Example of too many dependencies:

```csharp
public class OrderService
{
    public OrderService(
        ILoggerService logger,
        IEmailService email,
        IPaymentService payment,
        IInventoryService inventory,
        IShippingService shipping)
    {
    }
}
```

Better approach: split responsibilities into separate services.

---

# Disposal of Services

The **DI container automatically disposes services** that it creates.

Service disposal depends on lifetime:

| Lifetime  | Disposal Time        |
| --------- | -------------------- |
| Transient | End of scope/request |
| Scoped    | End of request       |
| Singleton | Application shutdown |

---

## Disposable Service Example

Transient service:

```csharp
public class TransientDisposable : IDisposable
{
    public void Dispose()
    {
        Console.WriteLine("TransientDisposable.Dispose()");
    }
}
```

Scoped service:

```csharp
public class ScopedDisposable : IDisposable
{
    public void Dispose()
    {
        Console.WriteLine("ScopedDisposable.Dispose()");
    }
}
```

Singleton service:

```csharp
public class SingletonDisposable : IDisposable
{
    public void Dispose()
    {
        Console.WriteLine("SingletonDisposable.Dispose()");
    }
}
```

Registration:

```csharp
builder.Services.AddTransient<TransientDisposable>();
builder.Services.AddScoped<ScopedDisposable>();
builder.Services.AddSingleton<SingletonDisposable>();
```

Creating scopes:

```csharp
using var scope = serviceProvider.CreateScope();

var transient = scope.ServiceProvider.GetRequiredService<TransientDisposable>();
var scoped = scope.ServiceProvider.GetRequiredService<ScopedDisposable>();
var singleton = scope.ServiceProvider.GetRequiredService<SingletonDisposable>();
```

---

# Services Not Created by Container

If a service instance is created manually, the container **will not dispose it automatically**.

Example:

```csharp
builder.Services.AddSingleton(new ExampleService());
```

Here:

* Instance is created by developer
* Container does not manage disposal
* Developer must dispose it manually

---

# IDisposable Guidelines

### Do not manually dispose services resolved from the container.

Example:

```csharp
public class MyService
{
    private readonly IDisposableService _service;

    public MyService(IDisposableService service)
    {
        _service = service;
    }
}
```

The DI container handles disposal automatically.

---

### Do not register IDisposable transient services if they must be disposed early

Instead use a **factory pattern**.

Example:

```csharp
public class FileServiceFactory
{
    public FileService Create()
    {
        return new FileService();
    }
}
```

---

### Shared Instance With Limited Lifetime

Use **scoped lifetime** and create a scope manually.

Example:

```csharp
public class Worker
{
    private readonly IServiceScopeFactory _scopeFactory;

    public Worker(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    public void Run()
    {
        using var scope = _scopeFactory.CreateScope();

        var service = scope.ServiceProvider.GetRequiredService<MyService>();

        service.Execute();
    }
}
```

---

# Built-in Container vs Third Party Containers

.NET provides a built-in DI container.

Use another container only if special features are required.

Examples of third-party containers:

* Autofac
* DryIoc
* Grace
* LightInject
* Lamar
* Stashbox
* Simple Injector

# Thread Safety

Singleton services must be **thread-safe** because they are shared across multiple requests.

Example:

```csharp
public class CounterService
{
    private int _count = 0;

    public int Increment()
    {
        return Interlocked.Increment(ref _count);
    }
}
```

Registration:

```csharp
builder.Services.AddSingleton<CounterService>();
```

# DI Recommendations

### Avoid Service Locator Pattern

Bad example:

```csharp
public class OrderService
{
    private readonly IServiceProvider _provider;

    public OrderService(IServiceProvider provider)
    {
        _provider = provider;
    }

    public void Process()
    {
        var service = _provider.GetService<IEmailService>();
        service.Send();
    }
}
```

Correct approach:

```csharp
public class OrderService
{
    private readonly IEmailService _emailService;

    public OrderService(IEmailService emailService)
    {
        _emailService = emailService;
    }

    public void Process()
    {
        _emailService.Send();
    }
}
```

---

### Avoid Calling BuildServiceProvider During Registration

Bad example:

```csharp
var provider = services.BuildServiceProvider();
var service = provider.GetService<MyService>();
```

Correct approach:

```csharp
services.AddSingleton<MyService>();
```

---

### Avoid Static Access to Services

Bad example:

```csharp
public static IServiceProvider Provider;
```

Correct approach:

Use constructor injection.

---

### Keep DI Factories Fast and Synchronous

Example:

```csharp
services.AddSingleton<MyService>(sp =>
{
    return new MyService();
});
```

Avoid asynchronous factories.

---

# Captive Dependency (Lifetime Mismatch)

Occurs when a **longer lifetime service depends on a shorter lifetime service**.

Bad example:

```csharp
builder.Services.AddSingleton<Foo>();
builder.Services.AddScoped<Bar>();
```

Implementation:

```csharp
public class Foo
{
    private readonly Bar _bar;

    public Foo(Bar bar)
    {
        _bar = bar;
    }
}
```

Here:

```
Singleton → Scoped dependency
```

This causes incorrect behavior.

---

# Scoped Service Becoming Singleton

Bad example:

```csharp
var service = serviceProvider.GetRequiredService<ScopedService>();
```

If resolved from root container, the scoped service effectively becomes singleton.

Correct approach:

```csharp
using var scope = serviceProvider.CreateScope();

var service = scope.ServiceProvider.GetRequiredService<ScopedService>();
```

---

# Summary

Key guidelines when using Dependency Injection:

* Design services to depend on interfaces
* Avoid static/global state
* Do not manually dispose services from DI
* Use correct service lifetimes
* Avoid service locator pattern
* Ensure singleton services are thread-safe
* Avoid lifetime mismatches
* Prefer constructor injection
